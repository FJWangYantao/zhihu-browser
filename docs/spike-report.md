# M0 技术验证报告

> **日期**：2026-09-28 · **环境**：Windows，Chrome 153，已登录知乎 · **工具**：[M0 探针](../spike/m0-probe/)，第一轮 0.1.0，第二轮 0.1.1
> 对应[项目计划](./plan.md)中 M0 的检查清单。本文只包含汇总后的结论和数字，原始报告不提交到仓库（第一轮的报告含有一处用户标识，见[第 5 节](#5-探针自身的问题)）。

## 1. 结论一览

**M0 完成，技术路线成立，可以进入 M1。** Edge 和 Firefox 没有测，分别放到 M1 和 M2。

| # | 检查项 | 结论 | 说明 |
|---|---|---|---|
| 1 | 首屏数据与接口结构 | ✅ | 覆盖首页、关注、热榜、问题页、回答页、专栏文章、搜索、用户主页，共 77 种接口，包括评论接口 |
| 2 | 拦截并改写接口响应 | ✅ 有一个坑 | 18 次页面加载拦到 1049 次接口请求，没有遗漏；删减数据后页面正常；但**整页被删空时，知乎会不停地请求下一页** |
| 3 | 首屏：预隐藏 / 启动前改写 | ✅ 结论明确 | 总能在知乎前端启动前读到首屏数据，但**删掉首屏数据里的回答，页面照样显示它**。服务端渲染的内容只能在元素层隐藏；预隐藏在回答页上 18–47 ms 内就处理完 |
| 4 | 从内容元素找到数据 | ✅ | 首页、问题页、回答页、用户主页 100% 找到 id，关注页 9/11、搜索页 56/60；各方式给出的 id 除第一轮回答页上的 1 次外都一致，且都能在数据中对上（链接这种方式最不可靠）。热榜用 `.HotItem`；专栏文章页没有 `.ContentItem`，需要单独适配 |
| 5 | 单页应用路由 | ✅ | 11 次跳转全部被 Navigation API 和 history 补丁立即发现 |
| 6 | 用户脚本环境 | ✅ | 隔离、同步通信、向已有环境注入代码都可行；后台被回收后重新启动时，一次消息往返最长约 0.3 秒 |
| 7 | 知乎自带暗色 | ⚠️ 不完整 | 切换 `data-theme` 和打开 `?theme=dark` 都不能让顶部导航栏完整变暗，主题插件需要自己补样式 |
| 8 | Edge / Firefox | ⏭ 未测 | Edge 在 M1 开发时顺带验证，Firefox 放到 M2 |

## 2. 第一轮：主要页面与接口

### 2.1 首屏数据（`js-initialData`）

两轮共 17 次加载读到了首屏数据：每次都在页面解析过程中（`loading`）、知乎前端启动**之前**，一次就解析成功，在它之前只有 1 个外部脚本。

| 页面 | 大小 | 实体数量 | 首屏内容从哪来 |
|---|---|---|---|
| 首页推荐 | 18 KB | 只有 `users: 1`（当前用户） | **接口**：前端启动后请求 `/api/v3/feed/topstory/recommend`，约 2 秒后出现在页面上 |
| 回答页 | 25–41 KB | `answers: 1`、`questions: 1`、`users: 1` | 服务端渲染 |
| 专栏文章 | 32 KB | `articles: 1`、`columns: 1`、`users: 2` | 服务端渲染 |
| 用户主页 | 21 KB | — | — |

- 顶层字段：`initialState`、`subAppName`、`spanName`、`canaryConfig`（专栏页还有 `fetchHost`）；`initialState.entities` 下有 answers、articles、questions、users、pins、zvideos、comments 等 22 类实体。
- 首页的过滤可以全部在接口层完成；回答页、专栏文章等服务端渲染的页面，内容已经在 HTML 里（见 [3.2](#32-删掉首屏数据里的回答)）。
- 第一轮有 1 次回答页加载既没有首屏数据，也没有任何接口请求，第二轮没有复现。

### 2.2 接口

两轮共见到 77 种接口（按路径算 68 种），其中 75 种的请求带 `x-zse-96` 签名头。这印证了"只旁听、不自己请求"的原则：自己发请求就得伪造签名。和插件相关的主要是：

| 接口 | 用在哪 | 条目类型（`data[].type`） | 要点 |
|---|---|---|---|
| `/api/v3/feed/topstory/recommend` | 首页推荐 | `feed` | `target.type` 为 answer / article；`target.content` 里就有**正文 HTML**，还有摘要、赞同数、评论数、创建与更新时间、作者（含 `url_token`）、问题标题；两轮共 400 多条内容里没有见到广告 |
| `/api/v3/moments` | 关注 | `feed`、`feed_advert`、`feed_group` | 广告是 `feed_advert` 条目；`feed_group` 里嵌套 `list[]`；动作见 `verb`（赞同、回答、提问、发想法） |
| `/api/v4/questions/:id/feeds` | 问题页 / 回答页的回答列表 | `question_feed_card` | **广告不在列表里**，而是响应顶层的 `ad_info`（带 `position`）；翻页有 `cursor` 和 `offset` 两种参数组合 |
| `/api/v3/feed/topstory/hot-lists/total` | 热榜 | `hot_list_feed` | 卡片式结构：`title_area`、`excerpt_area`、`metrics_area`、`link`，不是内容实体 |
| `/api/v4/search_v3` | 搜索 | `search_result`、`zvideo` | `object.type` 为 answer / article / question / zvideo；付费内容有 `paid_info.type = paid_column_content` |
| `/api/v4/comment_v5/…` | 评论 | `comment` | 见 [3.4](#34-评论) |

### 2.3 拦截与改写

- **覆盖率**：两轮 18 次页面加载，钩子拦到 1049 次接口请求，浏览器资源计时记录 1048 次，没有漏掉的接口。
- 18 次里有 5 次，`window.fetch` 在我们之后又被别的代码包了一层（可能是知乎的监控脚本，也可能是其他扩展），拦截不受影响。这说明拦截必须在 `document_start` 最早安装。
- **去掉一半条目**：10 个推荐流响应从 6 条删到 3 条，页面正常，没有报错。
- **去掉全部条目**：16 个响应被删空，每次知乎前端都在 1.1–1.6 秒后请求下一页，20 秒内连续请求了 16 次，页面上始终没有新内容。从数据上分不清是自动触发还是滚动触发，但结论相同：**整页被删空会造成"看不到内容、请求不停"**，这在风控上有风险。

### 2.4 从内容元素找到数据

对每个 `.ContentItem` 用 4 种方式找内容 id（第二轮改进了 microdata 的取法）：

| 页面 | 轮次 | 内容元素 | `data-zop` | microdata | 链接 | React 属性 | 各方式一致 | 在数据中找到 |
|---|---|---|---|---|---|---|---|---|
| 首页推荐 | 1 | 42 | 42 | — | 42 | 42 | 42 | 42 |
| 首页推荐 | 2 | 6 | 6 | 6 | 6 | 6 | 6 | 6 |
| 问题页 | 2 | 16 | 16 | 16 | 16 | 16 | 16 | 16 |
| 回答页 | 2 | 3 | 3 | 3 | 1 | 3 | 3 | 3 |
| 关注 | 1 | 11 | 9 | — | 9 | 9 | 9 | 9 |
| 搜索 | 1 | 60 | 45 | — | 56 | 56 | 56 | 56 |
| 用户主页 | 1 | 7 | 7 | — | 7 | 7 | 7 | 7 |

- `data-zop`（字段 `authorName`、`itemId`、`title`、`type`）覆盖回答和文章；搜索页的想法等卡片没有它，靠链接或 React 属性补上。
- React 属性（`data`、`answer`、`article`、`pin`、`content`、`item` 等）在所有内容元素上都有，但**只有页面主环境（MAIN world）能读到**。
- 链接最不可靠：回答页 3 个元素只有 1 个能从链接找到 id。第一轮回答页上出现过一次各方式不一致，第二轮记录了不一致的组合，结果没有复现。
- microdata（`dateCreated`、`dateModified`、`upvoteCount`、`commentCount` 等）在元素内找到带内容 id 的那个 `url` 后，命中率 100%，也适合取日期和数量。
- 找到的 id 100% 能在首屏数据或接口数据中对上，说明"数据层 + 元素识别"的方案可行。
- 带 `css-xxxxxx` 哈希类名的元素在主站占 25–47%，**专栏文章页高达 69%**，印证了"禁止依赖哈希类名"。

### 2.5 路由

两轮 11 次页面切换，每次都是 Navigation API 最先发现；`pushState` / `replaceState` 补丁也都在 0 ms 内发现；轮询要 88–599 ms 才发现，没有只靠轮询才发现的情况。

### 2.6 用户脚本环境（Chrome 153）

- `userScripts` 可用；用 `worldId` 配置并注册两个独立环境都成功。
- 两个环境都看不到页面的全局变量、扩展隔离环境的全局变量，也看不到对方。
- 与扩展隔离环境通过 DOM 事件同步通信：每轮 200 次全部同步完成，中位数约 0 ms，最慢 0.2 ms。
- `userScripts.execute()` 能向已打开页面里的已有环境执行代码，热重载可行。
- 事件里的对象数据跨环境可读；`customElements` 在扩展隔离环境和用户脚本环境里都不可用。
- 与后台的扩展消息往返：第一轮中位数 1.4 ms、最慢 5.9 ms；第二轮中位数 7 ms、**最慢 275 ms**。最慢的那次很可能是后台 service worker 被浏览器回收后重新启动。

## 3. 第二轮：补测结果

### 3.1 问题页与回答页

- 问题页（站内跳转进入）16 个回答，4 种方式全部找到 id 且一致。
- 回答列表接口 `questions/:id/feeds` 有 `cursor` 和 `offset` 两种翻页参数组合，适配时都要处理。

### 3.2 删掉首屏数据里的回答

- 在回答页上，于知乎前端启动前删掉 `entities.answers` 里唯一的那条回答：页面照常显示这条回答，没有报错。
- 同时出现了一次 `/api/v4/answers/:id` 请求，而第一轮的回答页加载都没有这个请求。很可能是前端发现数据缺失后，又取了一次。
- **结论**：服务端渲染的内容不能靠改首屏数据来隐藏，改了反而会让知乎多发一次请求。

### 3.3 预隐藏

- 回答页（服务端渲染）3 次：
  - 页面开始加载后 18–47 ms 内完成首次处理；
  - 每次 6 个元素分 3 批，最慢一批 2.3–6.2 ms；
  - 隐藏样式每次都生效，没有触发超时放行。
- 首页的内容来自接口，第一批元素约 2 秒后才出现，预隐藏在首页没有必要。
- 第一轮人工观察：没有闪烁。

### 3.4 评论

- 接口是 `comment_v5` 系列：`/api/v4/comment_v5/articles/:id/root_comment`（一级评论，每页 10 条）和 `/api/v4/comment_v5/comment/:id/child_comment`（楼中楼），请求带签名。
- 每条评论包括：
  - `content`（HTML）、`author`（含 `url_token`）；
  - `like_count`、`dislike_count`、`created_time`、`child_comment_count`；
  - `reply_comment_id`、`reply_root_comment_id`；
  - 状态标记 `is_author`、`hot`、`top`、`collapsed`；
  - IP 属地标签（`comment_tag` 中的 `ip_info`）。
- 本轮只在专栏文章上展开了评论，回答的评论接口没有出现。同属 `comment_v5`，预计结构一致，在 M1 确认。
- 页面上没有匹配到 `[class*="CommentItem"]`。探针只在跳转和滚动后采样，不能确定采样时评论区已经展开，评论的页面锚点留到 M1 用 React 属性确认。

### 3.5 专栏文章与热榜

- **专栏文章**：
  - 服务端渲染（见 2.1）；
  - 页面上没有 `.ContentItem`，文章本身带 `data-zop`；
  - 接口分布在 `zhuanlan.zhihu.com`（如 `/api/articles/:id/recommendation`）和 `www.zhihu.com` 两个域名下；
  - 页面报了 2 次 `ResizeObserver loop completed with undelivered notifications`（没开任何实验），是浏览器常见的无害警告。
- **热榜**：页面上有 30 个 `.HotItem`，与热榜接口返回的 30 条对应；没有 `data-zop`，要靠条目里的链接和接口数据对应。

### 3.6 暗色

- 第二轮在热榜页上用探针切换了两次 `data-theme`，页面背景和文字颜色都变了，与第一轮一致。
- 打开 `?theme=dark` 后的人工观察："导航栏还是没完整变暗"。
- 两轮人工观察一致：知乎自带的暗色样式不能完整覆盖导航栏。

### 3.7 其他

- 1 次首页加载出现 2 个未处理的 Promise 错误（没开过滤和改写），来源不明；其余加载都是 0。

## 4. 对计划和插件 API 的影响

1. **"数据优先"得到验证**：内容都能在数据里找到，而且正文 HTML 就在推荐流数据里，阅读模式和字数统计可以直接用数据。
2. **首屏按页面类型区分**：首页推荐的首屏内容来自接口，过滤在渲染前完成；回答页、专栏文章等服务端渲染的页面，用预隐藏样式加元素隐藏。**放弃"启动前改首屏数据"**。
3. **过滤不能让一页变空**：一页数据被全部过滤时，宿主保留一个占位条目（例如"已过滤 6 条"），连续多页为空时停止自动加载、改成"继续加载"按钮。M1 实现时改成了更简单的做法：这种情况不删数据，等知乎渲染后在页面上折叠（见插件 API 第 6 节）。
4. **广告有多种来源**：关注流的 `feed_advert` 条目、问题页回答列表顶层的 `ad_info`；推荐流本次没见到。适配层统一成 `kind: 'ad'`；问题页的广告不在回答列表里，插件 API 需要给它一个过滤入口（插件 API 待定问题 8）。
5. **锚点按页面区分**：
   - 信息流、问题页、回答页、搜索、用户主页用 `.ContentItem`，按 `data-zop` → React 属性 → microdata → 链接的顺序取 id；
   - React 属性由页面主环境里的一个小助手读取，并给元素打上 `data-zb-id` 标记；
   - 热榜用 `.HotItem`；
   - 专栏文章页和评论区单独适配。
6. **付费内容标记**：搜索结果里有 `paid_info`；推荐流等其他接口的对应字段在 M1 中确认。
7. **主题**：知乎的 `data-theme` 暗色样式覆盖了大部分页面，导航栏由主题插件自己补齐。
8. **后台不在关键路径上**：后台可能被浏览器回收，冷启动时一次往返最长约 0.3 秒。
   - 用户插件启动时需要的设置随 `userScripts` 注册代码一起注入，设置变化时更新注册；
   - 官方插件在扩展隔离环境里直接读 `chrome.storage`，不经过后台。
9. **挂载点**：两个环境都没有 `customElements`，挂载点用普通元素加 Shadow DOM（与计划一致）。
10. **路由检测**：Navigation API 加 history 补丁即可，轮询只作兜底。
11. **跨环境通信**：Chrome 上对象数据可以直接跨环境传递，但为兼容 Firefox，仍然统一传 JSON 字符串。

## 5. 探针自身的问题

第一轮的原始报告里有一个**用户标识**（打开过的那个用户主页地址里的那段），出现在 4 处：

- 3 个接口地址里，形如 `/api/v3/moments/<标识>/activities` 和 `/api/v4/profile/<标识>/infinity`；
- 用户主页首屏数据结构里的一个键（`people.profileStatus`）。

原因是 0.1.0 只替换了 `/people/`、`/org/`、`/members/` 后面的那段，并且只折叠有两个以上键的映射。

0.1.1 的修复：
- 页面地址和数据里出现过的用户标识（`url_token`）会被记下，并从地址、结构、错误信息里一律抹掉；
- 增加了 `/moments/<标识>/…`、`/profile/<标识>/…` 等形式，以及"含数字的连字符串"的识别；
- 只有一个键的映射也会被折叠。

冒烟测试加入了这几种情况：0.1.0 在这些检查上失败，0.1.1 全部通过。第二轮报告里没有再出现用户标识。

之后复查第一轮报告，又发现一处：有的映射以内容网址为键（`link_card_info`，形如 `https://www.zhihu.com/question/<id>/answer/<id>`），共 3 处，带出了公开回答的 id。这不是用户标识，但同样不应该出现在报告里。原因是折叠映射时只认"像 id 的键"，网址不在其中。0.1.2 把含 `/` 或 `:` 的键也当作 id 折叠，冒烟测试加了对应的检查（0.1.1 失败，0.1.2 通过）。第二轮报告里没有这种键。
